- 用户输入 `/review-plan`
- 用户输入 `/review-plan <方案内容>`（直接带方案）

## 方案来源优先级

1. **手动输入优先**：如果用户在调用时直接附带了方案文本，以手动提供的为准
2. **对话上下文**：如果用户没有手动提供，从当前对话历史中查找 AI 最近一次给出的方案/计划/设计
3. **都没有则索要**：友善地提示用户粘贴方案内容

## 评审流程

### Step 1: 理解方案与问题

先快速理解两个东西：

**A. 方案内容**：技术选型、架构设计、关键决策、实施步骤。

**B. 要解决什么问题**：从上下文推断用户原本的需求/痛点/背景。如果调用时用户直接说了"帮我看看这个方案能不能解决我的问题"，就从用户的描述中提取原始需求。

### Step 2: 问题对准度预审

在技术评审之前，先回答一个根本问题：**这个方案真的能解决用户的问题吗？**

这是一个独立的预审步骤，与后续的技术评审并行执行。

**🎯 问题对准度检查清单：**

| 检查项 | 说明 |
|-------|------|
| 问题定义是否清晰 | 方案是否明确定义了要解决什么问题 |
| 覆盖范围是否匹配 | 方案解决的问题范围是否与用户需求一致（不遗漏、不扩大） |
| 是否针对根因 | 方案解决了问题的根因，还是只处理了表象 |
| 能否验证 | 方案实施后如何验证问题确实被解决了（验收标准） |
| 是否有 trade-off | 方案引入了哪些新问题或副作用 |
| 是否有更简方案 | 有没有更简单、成本更低的方式能达到同样效果 |

每项标注状态：
- ✅ **通过** — 方案明确覆盖
- ⚠️ **部分覆盖** — 提到了但不够
- ❌ **缺失** — 未涉及
- 📄 **N/A** — 不适用

**评分（1-10）**：综合判定方案与问题的匹配度。如果评分低于 4 分，强烈建议先重新审视方案方向，不要在错误的方向上继续优化。

### Step 3: 并行评审（4 个子代理）

将问题对准度 + 6 个技术维度分成 4 组，用 **并行子代理** 同时评审：

| 代理 | 评审维度 |
|------|---------|
| **问题对准组**（alignment-agent） | 🎯 问题对准度（预审 + 独立子代理） |
| **架构可行性组**（feasibility-agent） | 🛠️ 可行性 + 🏗️ 架构合理性 |
| **安全性能组**（security-agent） | 🔒 安全性 + ⚡ 性能考量 |
| **边界质量组**（quality-agent） | 🔄 边界情况处理 + 📖 可维护性 |

每个子代理独立执行，互不干扰，生成各自的评审报告。

> **⚠️ 零上下文约束**：每个子代理**不接收对话历史**，不知道这个方案为什么写、之前讨论过什么。只基于方案文本 + 代码库做判断。防止锚定效应——同一个模型审自己参与写的方案，容易沿着原思路走，发现不了"这条路根本不通"。

#### 每个维度的评审结构

每个子代理对负责的 2 个维度，按以下结构逐一评审：

**Step A — 核对检查清单（Baseline）**
每个维度有一份固定的检查清单，逐项标注状态：

- ✅ **通过** — 方案明确覆盖了此项
- ⚠️ **部分覆盖** — 方案提到了但不够完整
- ❌ **缺失** — 方案完全未涉及此项
- 📄 **N/A** — 此项不适用于本方案

**Step B — 识别硬伤（Hard Violations）**
检查清单中发现明确错误的项，标记为硬伤。硬伤是"不修不行"的问题，比如：方案要求在 Windows 上跑 Docker Linux 容器但没有 WSL2；方案使用了 GPL 库但项目是闭源商业软件。

**Step C — 主观评分（1-10）**
综合清单核查和硬伤情况给出评分，评分必须有具体的正面/负面理由。

#### 各维度检查清单

**🛠️ 可行性**

| 检查项 | 说明 |
|-------|------|
| 技术是否成熟 | 所用技术是否经过生产验证，还是刚出的 beta 版 |
| 依赖是否可得 | 第三方服务/库是否可用，有没有 license 冲突 |
| 团队是否有能力 | 方案所需技能团队是否具备 |
| 时间估计是否现实 | 排期是否留有缓冲 |
| 资源需求是否合理 | 服务器/API/存储成本是否可接受 |
| 是否有 fallback 方案 | 关键技术选型如果失败是否有备选 |

**🏗️ 架构合理性**

| 检查项 | 说明 |
|-------|------|
| 模块职责是否清晰 | 单一职责原则，边界明确 |
| 依赖方向是否正确 | 高层不依赖低层细节（依赖倒置） |
| 是否过度设计 | 抽象层次是否匹配当前需求（YAGNI） |
| 扩展性如何 | 新增功能是否需要大改 |
| 数据流是否清晰 | 数据从哪里来、怎么处理、存哪里 |
| 外部接口设计是否合理 | API 契约是否稳定、版本化 |

**🔒 安全性**

| 检查项 | 说明 |
|-------|------|
| 认证与鉴权 | 谁可以做什么，最小权限原则 |
| 数据传输安全 | 是否 HTTPS/TLS，证书管理 |
| 数据存储安全 | 敏感信息是否加密存储 |
| 注入防护 | SQL/XSS/命令注入防护 |
| 限频/防刷 | API 是否有限频、防暴力枚举 |
| 日志安全 | 不记录密码/token 等敏感信息 |
| 依赖安全 | 三方库是否有已知漏洞 |

**⚡ 性能考量**

| 检查项 | 说明 |
|-------|------|
| 是否有性能目标 | 明确 QPS、P95 延迟目标 |
| 瓶颈分析 | 哪里可能是瓶颈，有无数据支撑 |
| 缓存策略 | 是否有合适的缓存层级 |
| 并发设计 | 锁/事务/竞争条件处理 |
| 数据量预估 | 数据增长预期和存储规划 |
| 扩展方式 | 垂直扩展还是水平扩展 |

**🔄 边界情况处理**

| 检查项 | 说明 |
|-------|------|
| 错误处理 | 异常捕获、错误码、用户提示 |
| 超时设计 | 外部调用是否有超时和重试 |
| 降级策略 | 依赖不可用时系统行为 |
| 幂等性 | 重复请求是否安全 |
| 数据一致性 | 最终一致性还是强一致性，补偿机制 |
| 输入验证 | 边界值、空值、恶意输入 |
| 并发冲突 | 多人同时操作的处理 |

**📖 可维护性**

| 检查项 | 说明 |
|-------|------|
| 代码组织 | 目录结构、模块划分是否清晰 |
| 配置管理 | 环境配置是否外置（12-Factor） |
| 日志/监控 | 关键链路是否有日志和告警 |
| 测试策略 | 单元测试/集成测试/端到端测试覆盖 |
| 部署方式 | CI/CD、蓝绿部署、回滚方案 |
| 文档 | 架构文档、API 文档、运维文档 |
| 技术债管理 | 是否有计划偿还已知技术债 |

## 评审原则

- **客观公正**：基于方案本身的实际内容评分，不因方案来自 AI 而加分或减分
- **硬伤优先**：硬伤是客观依据支持的"肯定错了"，评分是主观判断
- **不强制打分**：方案未涉及某维度时标注"N/A"，不强行编造评分
- **可追溯**：每个评分和判断都要有具体理由，不能笼统
- **建设性**：改进建议要具体可操作，能落地
- **引用标准**：尽可能引用业界标准作为依据（OWASP、12-Factor、SOLID、ACID 等）

## 参考标准

评审时可引用的业界标准：

- **安全**：OWASP Top 10、CWE Top 25
- **架构**：SOLID 原则、12-Factor App、Clean Architecture
- **可维护性**：约定优于配置、最少知识原则（Law of Demeter）
- **性能**：CAP 定理、CQRS 模式
- **可靠性**：设计冗余、优雅降级、幂等设计、断路器等模式

## 当信息不足时

如果方案内容不完整，不足以进行完整评审：
1. 标注"信息不足以评估"的维度
2. 列出缺失的关键信息
3. 友善提示用户补充后再评审
