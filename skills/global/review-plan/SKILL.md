## 触发方式

- 用户输入 `/review-plan`
- 用户输入 `/review-plan <方案内容>`（直接带方案）

## 方案来源

用户调用时直接附带方案文本（`/review-plan <方案>`）。若未附带，友善提示粘贴即可——**不从对话历史中猜测方案**，猜错方案会让整份评审跑偏。

## 评审流程

### Step 1: 理解方案与问题

先快速理解两个东西：

**A. 方案内容**：技术选型、架构设计、关键决策、实施步骤。

**B. 要解决什么问题**：从上下文推断用户原本的需求/痛点/背景。如果调用时用户直接说了"帮我看看这个方案能不能解决我的问题"，就从用户的描述中提取原始需求。

**可评审性门禁（先于 Step 2 执行）**：

检查方案是否具备三项基本要素：**要解决的问题、目标/范围、至少一条实施路径**。

- 三项齐全 → 继续 Step 2
- 缺两项及以上 → 中止评审，提示用户补齐后再来，不硬跑后续维度（硬跑出来也是一堆 N/A）
- 缺一项 → 照常评审，但报告中该维度标注"信息不足"

### Step 2: 问题对准度预审

在技术评审之前，先回答一个根本问题：**这个方案真的能解决用户的问题吗？**

这是一个独立的预审步骤，先于技术评审完成。

**🎯 问题对准度检查清单：**

| 检查项 | 说明 |
|-------|------|
| 问题定义是否清晰 | 方案是否明确定义了要解决什么问题 |
| 覆盖范围是否匹配 | 方案解决的问题范围是否与用户需求一致（不遗漏、不扩大） |
| 是否针对根因 | 方案解决了问题的根因，还是只处理了表象 |
| 能否验证 | 方案实施后如何验证问题确实被解决了（验收标准） |
| 是否有 trade-off | 方案引入了哪些新问题或副作用 |
| 是否有更简方案 | 有没有更简单、成本更低的方式能达到同样效果 |
| 改动规模是否匹配 | 方案的修改量与问题严重度是否匹配：是小修小补还是大动干戈，有没有「杀鸡用牛刀」或「头痛医头」 |

每项标注状态：
- ✅ **通过** — 方案明确覆盖
- ⚠️ **部分覆盖** — 提到了但不够
- ❌ **缺失** — 未涉及
- 📄 **N/A** — 不适用

**评分（1-10）**：综合判定方案与问题的匹配度。如果评分低于 4 分，强烈建议先重新审视方案方向，不要在错误的方向上继续优化。

### Step 3: 技术维度评审

主代理在同一上下文中按以下顺序逐一评审 4 个维度：

🛠️ 可行性 → 🏗️ 架构合理性 → 🔗 跨模块影响 → 🔄 边界情况处理

> **提示**：只基于方案文本与代码库判断，警惕顺着方案原有思路走——发现"这条路根本不通"比修补细节更重要。

#### 每个维度的评审结构

每个维度按以下结构逐一评审：

**Step A — 核对检查清单（Baseline）**
每个维度有一份固定的检查清单，逐项标注状态：

- ✅ **通过** — 方案明确覆盖了此项
- ⚠️ **部分覆盖** — 方案提到了但不够完整
- ❌ **缺失** — 方案完全未涉及此项
- 📄 **N/A** — 此项不适用于本方案

**Step B — 识别硬伤（Hard Violations）**
检查清单中发现明确错误的项，标记为硬伤。硬伤是"不修不行"的问题，比如：方案要求在 Windows 上跑 Docker Linux 容器但没有 WSL2；方案使用了 GPL 库但项目是闭源商业软件。

**Step C — 主观评分（1-10）**
综合清单核查和硬伤情况给出评分，评分必须有具体的正面/负面理由。

#### 各维度检查清单

**🛠️ 可行性**

| 检查项 | 说明 |
|-------|------|
| 技术是否成熟 | 所用技术是否经过生产验证，还是刚出的 beta 版 |
| 依赖是否可得 | 第三方服务/库是否可用，有没有 license 冲突 |
| 团队是否有能力 | 方案所需技能团队是否具备 |
| 时间估计是否现实 | 排期是否留有缓冲 |
| 资源需求是否合理 | 服务器/API/存储成本是否可接受 |
| 是否有 fallback 方案 | 关键技术选型如果失败是否有备选 |

**🏗️ 架构合理性**

| 检查项 | 说明 |
|-------|------|
| 模块职责是否清晰 | 单一职责原则，边界明确 |
| 依赖方向是否正确 | 高层不依赖低层细节（依赖倒置），与跨模块的循环依赖不是一回事 |
| 是否过度设计 | 抽象层次是否匹配当前需求（YAGNI） |
| 扩展性如何 | 新增功能是否需要大改 |
| 数据流是否清晰 | 数据从哪里来、怎么处理、存哪里 |
| 外部接口设计是否合理 | API 契约是否稳定、版本化 |

**🔗 跨模块影响**

> 专项回答「这个方案会波及哪些模块、影响多大」——评审原则要求警惕顺着方案原有思路走，这一步先把影响面摊开，再决定值不值得往下走。
>
> 本维度只看影响面与波及范围。架构层已评过的依赖倒置、数据流清晰度，此处**不重复扣分**。

| 检查项 | 说明 |
|-------|------|
| 受影响模块清单 | 方案会改动/新增/调用哪些模块，逐个列出来 |
| 接口契约变化 | API/协议/数据结构变更会波及哪些调用方，是否需要兼容旧版本 |
| 数据流 ripple | 数据来源、存储、流转的变化会牵动哪些上下游环节 |
| 依赖方向 | 新增依赖是否形成循环依赖或反向依赖（与架构层的依赖倒置是两回事） |
| 兼容性/迁移 | 是否破坏现有行为，是否需要灰度、迁移脚本或回滚方案 |
| 风险半径 | 最坏情况下影响范围多大，出问题能否快速回滚 |

**🔄 边界情况处理**

| 检查项 | 说明 |
|-------|------|
| 错误处理 | 异常捕获、错误码、用户提示 |
| 超时设计 | 外部调用是否有超时和重试 |
| 降级策略 | 依赖不可用时系统行为 |
| 幂等性 | 重复请求是否安全 |
| 数据一致性 | 最终一致性还是强一致性，补偿机制 |
| 输入验证 | 边界值、空值、恶意输入 |
| 并发冲突 | 多人同时操作的处理 |

### Step 4: 汇总评审报告

4 个维度全部评审后，按 `references/report-template.md` 的模板汇总成最终报告。

同时保存到当前工作目录 `review-plan-output-YYYY-MM-DD-HHmmss.md`（无工作目录时只在对话中输出，不落盘）。

## 评审原则

- **客观公正**：基于方案本身的实际内容评分，不因方案来自 AI 而加分或减分
- **硬伤优先**：硬伤是客观依据支持的"肯定错了"，评分是主观判断。任一维度出现 🔴 硬伤时，综合评分强制 ≤5/10、结论直接落到「不建议实施」，不参与加权平均——硬伤不是扣分项，是一票否决项
- **不强制打分**：方案未涉及某维度时标注"N/A"，不强行编造评分
- **可追溯**：每个评分和判断都要有具体理由，不能笼统
- **建设性**：改进建议要具体可操作，能落地
- **引用标准**：评分和建议尽可能引用业界标准作为依据（OWASP、12-Factor、SOLID、ACID 等）
